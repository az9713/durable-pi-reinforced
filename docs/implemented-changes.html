Each change

C1. Crash-test harness (G1-1)

What it does

A new test file starts a real backend with the free faux model. It kills the backend with SIGKILL while a tool or a job step runs. Then it starts the backend again and checks what happened to the tool and to its side effect. Each case kills at a point the test can see (a line in a file, a live tool task, a subagent id), not after a random delay. Thus a pass does not depend on timing luck.

The 8 cases (line = start of the case in crash.test.ts):

  1. :35 The built-in bash, read, write and edit tools report their replay policy.
  2. :46 bash cut off by SIGKILL comes back interrupted and does not run again.
  3. :65 An unsafe repo tool (ping_on_call_engineer) cut off by SIGKILL comes back interrupted and never pages.
  4. :81 A safe repo tool (update_state) cut off by SIGKILL applies its App State change once.
  5. :97 A job's subagent step cut off by SIGKILL admits its prompt once.
  6. :114 stuck reports nothing on an idle session; backup copies the database, and the session keeps working (C5, C9).
  7. :134 A lock from another boot is stale even when its PID is alive (C7). Skipped where /proc/sys/kernel/random/boot_id does not exist.
  8. :151 once() returns the stored result and never runs the effect twice (C2).
Where
  • New file crash.test.ts (163 lines). The helper crashSession() is at :14.
  • faux.ts:10 (comment) and faux.ts:73-76: a new scripted prompt, state: <operation> <path>[ <value json>], that makes one update_state call. Case 4 uses it.
  • No product code changed for C1.
Why

The README says that a bash call cut off by a restart comes back as "interrupted". That is true only if the built-in bash is unsafe, and that tool is in the pi-durable library, not in this repo. C2, C3 and every future tool depend on this fact. A label check alone is not enough, so the harness tests the behavior. Full reason.

Limit

Case 4 can miss the update_state call and kill the backend after the call ended. Its assert (one increment) is true in both cases, so the case cannot fail for that reason, but it does not always test a cut-off call.

C2. once(): one outside effect per tool task (G2-1)

What it does

A helper for a future tool that calls an outside service (Slack, email, a payment, a deploy). It first reads a receipt for this tool task. If the receipt says "done", it returns the stored result and does not call the service. If not, it calls the service with the idempotency key <session id>:<task id>, then writes the receipt with the result.

Where
  • extensions.ts:38-43 (doc comment) and extensions.ts:44-61 (export async function once). It uses the existing Receipt document at extensions.ts:31.
  • No tool uses once() yet. The two older copies of the receipt pattern (update_state, run_durable_job, at extensions.ts:173 and :250) are unchanged.
Why

pi-durable gives a tool with an outside effect two choices, and both have a cost pd-doc. unsafe: a crash during the call returns interrupted, and the model must guess if the effect happened. safe with no key: the call runs again, so the effect can happen twice. With once(), a tool can be safe and still not repeat the effect. Full reason.

Checked by

Case 8 (crash.test.ts:151), with a stub API in place of a real tool task.

Limit

A crash after the outside call and before the receipt commit makes the call run again, with the same key. This is safe only if the service ignores a repeated key, or lets you ask "did key X run?". A service with neither keeps a gap that this code cannot close.

C3. Stored values for job steps (G2-3)

What it does

A durable job runs in phases, and each phase runs steps (usually shell commands). After a crash, the job starts the interrupted phase again from its start. Now each finished step stores its value. On the resume, a step that finished before the crash returns its stored value and does not run its command again.

Where
  • jobs.ts:43-49: a new task-scoped document, kind demo.job-step-values, that holds the value of each step by step id.
  • jobs.ts:429 onward, step(): lines 431-433 return a stored value if one exists; lines 438-443 write the "done" record and the value in one commit, so a step is fully recorded or not recorded.
  • jobs.ts:689-702, the resume branch: keeps the finished steps that have a stored value and removes the others. Line 701 writes the "Resumed from the last checkpoint" note with the fixed id <phase>:<iteration>:resumed.
Why

Today the three example jobs run only read commands, so a repeated step costs only time. The first job step with an effect (git commit, npm publish, curl -X POST) would run twice after a crash. Full reason.

The fixed note id is a fix found during the build. The old code wrote the note with p.note(), which took step number 0. That moved every later step id by one, so stored values would match the wrong steps.

Checked by

Type check only. No job step has an effect that a test can count.

Limit

(1) Step ids come from the call order. A handler whose steps change order on a resume (for example, steps that depend on time or outside input) gets the wrong stored values. Today's handlers call steps in a fixed order. (2) A crash during the command itself still runs it again. (3) A p.shell() call outside p.step() has no stored value. Today every shell() call is inside a step().

C4. Retry Jev rows marked error (G2-4, demo)

What it does

The proactive demo sends each log row to Jev for a verdict. Before this change, a failed Jev call stored the row as error, and the watcher never sent it again. Now the watcher sends an error row again, at most once each 60 s, while the row is inside the backlog window. With the default 300 s window, that is about 4 retries for each row.

Where
  • watch-store.ts:92-99: errorsToRetry(ageMs, backlogMs, limit). It selects rows with status = 'error', judged more than ageMs ago, with a log time inside the backlog window, at most limit rows.
  • watcher.ts:113-115: poll() (starts at :103) calls errorsToRetry(60_000, backlogMs, 50) and queues the rows.
  • watcher.ts:74-75: a new pending set of row ids that are queued or in flight. enqueue() at :118-122 skips a row that is in the set; :132 removes the row when its call ends. poll() runs each 300 ms, so without this set one row could be queued many times.
Why

During a Jev outage, every row from that time stayed unjudged. Those rows never counted toward an incident, so a burst of real errors during the outage was never reported. A successful retry overwrites the error row, because saveVerdict already uses INSERT OR REPLACE. Full reason.

Checked by

Type check only. The demo has no tests.

Limit

The retry query scans the verdicts table each 300 ms (marked ponytail: at watcher.ts:114). Add an index on (status, judged_at) if the table grows past demo size.

C5 + C11. Report stuck work (G3-2, G3-1)

What it does

A new read-only route returns two lists. queued (C5): follow-up messages in a conversation where no foreground work runs; nothing will run them until a new message or a withdraw. blocked (C11): tasks that no registered definition can run. The route changes nothing. A person acts with the existing routes: withdraw the follow-up, or put back the task definition, or abort the task (it then ends orphaned).

Where
  • store.ts:915-935: Store.stuck(h), with its doc comment. It reads h.inspect(ctx). Lines 922-924 count a conversation as busy if it has a task that is not blocked and not a background task.
  • routes.ts:95: GET /v1/sessions/:s/stuck.
  • API.md:32: the route row, with the response shape {blocked:[{taskId,kind,conversationId,reason}], queued:[{submissionId,conversationId}]}.
Why

C5: after a failed run, queued follow-ups wait, and their wait() does not end, until the next submission or a withdraw pd-doc. With no person present, the messages never run. C11: a task whose definition is missing, too old, or failed to migrate stays live and blocked, and nothing ends it pd-doc. This can happen if you rename or re-version a job while a run is live. Decision: report only, no automatic resend, because a resend costs model spend and can send an old message into a changed context. C5 reason, C11 reason.

Checked by

Case 6 (crash.test.ts:114) checks that an idle session reports two empty lists. No case creates a stuck follow-up or a blocked task.

Limit

The build does not count background tasks as busy. Whether queued follow-ups wait behind a background job is unverified. If they do wait, the route reports such a follow-up as stuck while it is only waiting.

C6. Start when the model catalog has gaps (G3-3)

What it does

Before this change, the backend did not start if one of the 29 curated models was missing from pi-ai's OpenRouter catalog, or if the live model list did not load in 10 s. Now a missing model is logged and left out, and a failed live list is logged and replaced by the built-in catalog. The backend fails only if none of the curated models exist.

Where
  • store.ts:165: new field present, the curated models that the catalog has.
  • store.ts:199-207, constructor: filters the curated models, logs OpenRouter catalog missing <id>; it is left out for each missing one, throws only when present is empty.
  • store.ts:284-287, defaultModel(): uses defaultModelId if it is present, else the first model in present.
  • store.ts:302-307, loadModels(): a try/catch around getAvailable; on an error it logs [models] live model list failed; using the built-in catalog and uses the catalog read at construction.
  • routedModel() (store.ts:328) and validateModel() (store.ts:340) check against present (:336, :348). A session whose model disappeared moves to the default model when it opens.
Why

One renamed model id after a pi-ai upgrade, or a slow network at boot, stopped the whole device. Every session paused, and systemd restarted the backend each 2 s into the same failure. Full reason.

Checked by

Type check only. A run-time test needs OpenRouter and a catalog with a missing model.

Limit

Whether the built-in catalog needs the network is unverified.

C7. Detect a stale lock after a reboot (G3-4)

What it does

Each database has a lock file. Before this change, the file held only the owner's process id (PID), and a new start removed the lock only if that PID was dead. Now the file holds <pid> <boot id>. A lock written during an earlier boot is stale, even if a live process now has the same PID.

Where
  • store.ts:103-110: bootId, read once from /proc/sys/kernel/random/boot_id. It is empty where that file does not exist.
  • store.ts:112-139: lockFile(). Line 114 builds the owner string. Lines 120-123 read the held PID and boot id; a different boot id makes the lock stale. A file with the PID only (the old format) uses the PID check as before. Lines 134-138: unlock deletes the file only if it holds the exact owner string.
Why

After a reboot, PIDs are used again. A lock left by a crash before the reboot can name a live, unrelated process. Then the backend refuses to start with Database already owned by process N until a person deletes the lock file. pi-durable has no lock between processes pd-doc, so this lock is the only protection against two processes on one database. Full reason.

Checked by

Case 7 (crash.test.ts:134).

Limit

(1) macOS has no boot_id file, so macOS locks hold the PID only, as before. sysctl kern.boottime was not added, because it is unverified as independent of the wall clock. (2) A PID used again in the same boot still blocks a start.

C8. Log the Jev guard's skipped commands (G2-2)

What it does

The Jev damage-control guard judges each bash command before it runs. If Jev fails, the guard lets the command run with no verdict ("fails open"). Now each such command writes one line to standard error, which goes to backend.log. The change does not make the guard stronger. It makes its gaps visible.

Where
  • addons.ts:131: console.error("[jev-damage-control] unjudged, ran anyway:", command, "-", message), in the catch branch at :129-132.
  • addons.ts:8-9: a rule in the file header. A hook that asks a person or an outside API must store the answer with api.memo. A safe tool that runs again after a crash skips beforeTool.
Why

During a Jev outage, every bash command ran unjudged and left no trace. Full reason.

Checked by

Type check only.

Limit

The skipped beforeTool on a rerun is library behavior pd-doc. This change only documents it.

C9. Back up an idle session (G2-6)

What it does

A new route copies one session's database to the folder in DPI_BACKUP_DIR. You put that folder on another disk or a synced folder, and you call the route from cron. The session must be idle. The route closes the session, copies the files, and opens the session again.

Where
  • store.ts:937-973: Store.backup(row), with its doc comment. Without DPI_BACKUP_DIR it returns 503. With any live task or queued submission it returns 409 conflict ("Session is busy; try the backup later"). It copies agent.sqlite, plus -wal and -shm if they exist, to <DPI_BACKUP_DIR>/<session id>-<ms>/. It opens the session again in a finally block, so a failed copy still reopens the session.
  • routes.ts:96: POST /v1/sessions/:s/backup.
  • README.md:36: the DPI_BACKUP_DIR row, with a cron example. API.md:33: the route row.
Why

Each session is one agent.sqlite file on one disk. A disk failure lost every session. Also, an agent runs bash as the user that owns ~/.dpi, so one wrong command can delete its own database inferred. Option A (close, copy, reopen) stays inside the documented pi-durable contract: close writes no outcomes, so work resumes at the next open pd-doc. Full reason.

Checked by

Case 6 (crash.test.ts:114): the backup copies the database and the session keeps working after it.

Limit

The route copies session databases only. app-state.sqlite (shared by all sessions) and catalog.sqlite are not copied. A message sent during the copy waits until the session opens again.

C10. Restart on Windows through WSL2 (G2-7, docs only)

What it does

A new row in the README service table explains how to restart the backend automatically on Windows: run it as a systemd service inside WSL2, and start WSL2 at log on with a Task Scheduler entry. Nothing on this machine changed.

Where

README.md:58: the "Windows (WSL2)" row. The steps: (1) put [boot] and systemd=true in /etc/wsl.conf, then run wsl --shutdown; (2) declare the WSL2 machine as kind local with service: systemd and run just net up <id> (needs sudo -n); (3) schtasks /Create /TN "dpi-backend WSL" /SC ONLOGON /TR "wsl.exe -d Ubuntu --exec /bin/true".

Why

The repo's restart layer is systemd or launchd. Windows has none. On this machine, a crash or a reboot leaves every session paused until a person runs just backend run. Full reason.

Checked by

Not tested. Setting it up needs sudo and a Task Scheduler entry, and that was not done for this build.

Limit

Two points are unverified: whether WSL2 keeps the VM running with only the service running, and a restart with nobody logged on.

Findings from the test run

  1. The built-in bash is unsafe. Confirmed in the installed pi-durable source: dist/tools/bash.js sets no replay value, and the default is unsafe (dist/harness/tool.js:63, :73). Thus the README claim is correct: a cut-off bash call comes back interrupted and does not run again (case 2).
  2. The bash child process survives a backend SIGKILL. After the kill, the shell keeps running and finishes its command. Nothing reports that effect. "Does not run again" is true; "did not finish" is not.

How to run the tests

Run from the WSL2 Linux disk, not from /mnt/c. From /mnt/c the server does not start inside the 20 s limit of bootServer (tests/helpers.ts:69-76). The command copies the two apps to ~/dpi-test and runs the tests there. Set REPO to the WSL2 path of your clone:

REPO=/mnt/c/path/to/durable-pi-reinforced
mkdir -p ~/dpi-test/apps && rsync -a --delete "$REPO/apps/dpi-backend" "$REPO/apps/dpi-sdk" ~/dpi-test/apps/ && cd ~/dpi-test/apps/dpi-backend && npm test
