Group A: buildable in the repo (7)

C1. Verify the replay policy, then add a crash-test harness (G1-1)

What it is

Two parts.

  1. A one-request check. Ask a running backend for an agent's detail. The response lists every tool with its replay value, including the built-in bash, read, write and edit. The web Tools tab shows the same list (README.md:159).
  2. A crash-test file. A new test file kills the backend with SIGKILL while a tool runs, restarts it, and checks what happened to the tool and its side effect. It uses the free faux model, so it costs no model spend.
Why it is needed

The README says a bash call cut off by a restart comes back as "interrupted" (README.md:58). That is true only if the built-in bash tool is unsafe. Its definition is in pi-durable, and the package is not in this checkout. C2, C3 and any tool you add depend on this fact.

Part 1 alone is not enough. The route computes t.replay ?? "unsafe" (store.ts:712). If the library stores the policy somewhere other than the replay field, the route reports unsafe even when the real behavior differs inferred. Part 2 tests the behavior, not the label.

What breaks if not built

Now: nothing visible. The risk is in the decisions: if bash is actually safe, a cut-off bash call with a side effect (git push, a deploy script) runs again after a restart, and the docs say it does not.

Later: each pi-durable upgrade can change tool policies without notice (readme.md:7). Without this test, an upgrade that changes them goes unnoticed.

Files and sections
  • Read only, for part 1: store.ts:688-694 (toolsOf collects every tool of the agent's selected extensions; CodingTools is selected at store.ts:526) and store.ts:709-716 (the tools list with replay). Route: GET /v1/sessions/:s/agents/:a (apps/dpi-backend/API.md:34).
  • New file: apps/dpi-backend/tests/crash.test.ts. The test script tsx --test tests/*.test.ts (apps/dpi-backend/package.json:10) picks it up, so just check runs it inferred.
  • Reuses: helpers.ts (bootServer, tempStore, until, faux), the pattern of recovery.test.ts:8-31, and the faux model's scripted prompts: !<command> makes one bash call (faux.ts:44-47); page: <text> calls ping_on_call_engineer (faux.ts:71); job: <id> starts a job (faux.ts:58-64).
  • No product code changes.
The change

Five test cases, each run with a kill delay chosen at random between 50 ms and 3000 ms, so that repeated runs hit different points:

  1. Policy label. Read the agent detail. Record the replay value of bash, read, write, edit.
  2. bash cut off. Send !echo start >> runs.txt; sleep 5; echo end >> runs.txt. Kill during the sleep. Restart. If bash is unsafe: expect an interrupted tool result and exactly one start line. If safe: expect two start lines. Also record whether an end line appears: the shell child process may survive the backend's SIGKILL and finish on its own unverified. That would be an outside effect that nobody reports.
  3. Unsafe repo tool cut off. Send page: test. Kill during the 1.5 s pause (extensions.ts:375). Expect interrupted and Pager.paged still false.
  4. Safe repo tool cut off. Kill during an update_state call. Expect the App State change applied once (the receipt at extensions.ts:146-157).
  5. Subagent job step cut off. Start release-check, kill during the Gather phase. Expect one admitted subagent prompt (requestId: job:${task.id}:${spec.id}, jobs.ts:512).

Run it in WSL2: the cases need bash. Node 22.22.1 is enough (engines is >=22.19.0). Run it from the Linux disk, not /mnt/c: from /mnt/c the server does not start inside the 20 s limit of bootServer (helpers.ts:69-76).

As built. The file has 8 cases: the 5 above, plus stuck() and backup() on an idle session (C5, C9), a lock from another boot (C7), and once() with a stub API (C2). The cases kill at an observed point (the start line, a live tool task, a subagent id), not after a random delay, so the asserts do not depend on luck. Case 4 can miss the update_state call and kill after it ends; its assert (one increment) holds in both cases. The faux model has a new prompt, state: <operation> <path>[ <value json>], for case 4.

C2. Effect ledger for tools that call outside services (G2-1)

What it is

A small helper that wraps one outside call in a receipt. The receipt records "done, with this result". The call carries an idempotency key built from the task id. With the helper, a tool that calls an outside service can be declared replay: "safe": a rerun after a crash either returns the stored result or repeats the call with the same key, which the service ignores as a duplicate.

Why it is needed

pi-durable makes only the admission of a submission exactly-once (README.md:332). For a tool with an outside effect, it offers two choices, and both have a cost (spec.md:1853-1864) pd-doc:

  • unsafe: a crash mid-call returns interrupted, and the effect may or may not have happened. The model must guess, and it may call again.
  • safe with no key: the call runs again, so the effect can happen twice.

The library's own guidance is to pass an idempotency key such as `payment-${task.id}` (announcement.md:459-464). The repo already uses this pattern twice, without a shared helper.

What breaks if not built

Now: nothing. No current dpi-backend tool makes a real outside call. ping_on_call_engineer only simulates a page (extensions.ts:374-383). update_state and run_durable_job already use a receipt. In the demo, the deploy is already keyed by its task id.

Later: the first tool you add that posts to Slack, sends an email, charges a card or starts a deploy. As unsafe, every crash during the call leaves the model to guess whether to call again. As safe without a key, every crash during the call can repeat the effect.

Files and sections
  • extensions.ts:31-36: the Receipt document (scope: "task", fields applied and result). The helper goes next to it.
  • extensions.ts:146-157 (update_state) and extensions.ts:223-237 (run_durable_job): the two existing copies of the pattern. Changing them to use the helper is optional.
  • extensions.ts:357-393 (ping_on_call_engineer): do not change. It is unsafe on purpose, to demonstrate the interrupted result.
The change

As built (extensions.ts, exported once). No tool uses it yet:

// Run one outside effect at most once per tool task. `key` goes to the service as its idempotency key.
export async function once(api, ctx, sessionId: string, effect: (key: string) => Promise<string>) {
  const key = `${sessionId}:${api.taskId}`;
  const done = await api.commit(async (tx) => { const r = await tx.doc(Receipt, api.taskId); return r.applied ? r.result : undefined; }, ctx);
  if (done !== undefined) return done;          // a rerun after the effect was recorded
  const result = await effect(key);             // a rerun before this line repeats the call with the same key
  await api.commit(async (tx) => { const r = await tx.doc(Receipt, api.taskId); if (!r.applied) Object.assign(r, { applied: true, result }); }, ctx);
  return result;
}

Limit. A crash between the outside call and the receipt commit means the call runs again with the same key. This is safe only if the service accepts an idempotency key, or lets you ask "did key X happen?" before you call. A service with neither keeps a gap that no code here can close.

C3. Receipts for job steps (G2-3)

What it is

When a durable job phase resumes after a crash, it runs from the start of the phase again. This change stores each finished step's value. On a resume, a step that already finished returns its stored value instead of running its shell command again.

Why it is needed

Resumption is per phase and iteration, not per step. On resume, runPhase deletes the steps of the interrupted iteration (jobs.ts:681-682) and calls the phase handler again (jobs.ts:698-700). Only App State writes are deduplicated, by key (jobs.ts:439, 462-468), and the subagent prompt by requestId (jobs.ts:512).

What breaks if not built

Now: nothing. All three example jobs run only read commands: git rev-parse, git status, ls, find, cksum (jobs.ts:177-320). A resume repeats them and costs only time.

Later: the first job phase that runs a command with an effect (git commit, npm publish, curl -X POST). A crash after that command and before the phase's next checkpoint runs the command again.

Files and sections
  • jobs.ts:421-438: step() in phaseApi. Step ids are `${spec.id}:${cp.iteration}:${counter++}` (line 422).
  • jobs.ts:676-692: the resume branch of runPhase, which deletes the interrupted iteration's steps.
  • New: a task-scoped document (the same kind as Receipt, extensions.ts:31-36) that holds { [stepId]: value }.
The change
  1. In step(), before fn(): read the step-values document. If it has this step id, return the stored value and record the step as done, with the detail "from before the restart".
  2. In the commit that records the step as done (lines 427-429): also write the value to the document. Then a step is either fully recorded or not recorded.
  3. In the resume branch (lines 681-682): keep the steps that have a stored value. Delete only the others.

As built, two differences. (1) A skipped step is not written again: its kept record already says done, with its first detail. (2) The "Resumed from the last checkpoint" note used p.note(), which took step number 0 and moved every later step id by one, so stored values would match the wrong steps. The note is now written in the resume commit with the fixed id <phase>:<iteration>:resumed. The document kind is demo.job-step-values. No crash test covers C3: no job step has an effect to count.

Limits. (1) Step ids depend on call order. A handler whose steps depend on time or outside input can call them in a different order on a resume, and the stored values then match the wrong steps. Today's handlers call steps in a fixed order. (2) A crash during the command itself (between the "running" and "done" records) still runs it again. Only a command with its own key, as in C2, avoids that. (3) Calls to p.shell() outside p.step() are not covered. Today every shell() call is inside a step() (jobs.ts:274-278, 290-302).

C4. Retry Jev rows marked error (G2-4, demo)

What it is

The proactive demo sends each log row to Jev. If the call fails, the row is stored as error and never sent again. This change sends error rows again, at most once per minute per row, until the row is older than the backlog window.

Why it is needed

On a failure, judge() records status: "error" and returns (watcher.ts:155-157). poll() fetches only rows with no verdict row at all (watch-store.ts:82-86: v.log_id IS NULL). The watcher therefore never sees an error row again. Only rows that were in flight at a restart are judged again, because they have no verdict row (watcher.ts:92).

Two existing facts keep the change small. saveVerdict uses INSERT OR REPLACE (watch-store.ts:99), so a successful retry overwrites the error row without a schema change. The backlog window (--backlog, default 300 s, config.ts:32) already limits how long a row is worth judging, so it also limits the retries.

What breaks if not built

Now: during any Jev outage, every row in that period stays unjudged. Incident detection counts verdicts by log time in a 120 s window, so failures that happen during the outage never count toward the threshold of 3. The demo recovers only because the bug keeps producing new failing rows inferred.

Later: on a real log stream, a short burst of real errors during a Jev outage is never reported.

Files and sections
  • watch-store.ts: a new method next to unjudgedAfter (lines 82-89). The verdicts table (lines 62-76) already has status, log_ts and judged_at.
  • watcher.ts:101-112: poll() also queues the retry rows.
  • watcher.ts:68-73: a new set of row ids that are queued or in flight, so a row is not queued twice. poll() runs every 300 ms (line 93).
The change
-- watch-store.ts: error rows judged more than 60 s ago, still inside the backlog window
SELECT <log columns> FROM lg.logs l JOIN verdicts v ON v.log_id = l.id
WHERE v.status = 'error' AND v.judged_at < :now_minus_60s AND v.log_ts > :now_minus_backlog
ORDER BY l.id LIMIT 50

With a 60 s interval and the default 300 s backlog, a row is retried at most about 4 times, at about $0.00003 per call. A retried row whose log time is older than the 120 s incident window is judged, but it does not count toward a new incident. That matches the current rule that the window uses log time.

C5. Report follow-ups stuck after a failed run (G3-2)

What it is

A read-only check that lists queued follow-up messages in a conversation with no work running. The person then withdraws them with the existing route, or sends a new message. The check does not resend anything by itself (see open questions).

Why it is needed

"Failure and task abort leave the inbox alone. Queued follow-ups wait in pi.inbox, and their wait() does not settle, until the next submission's boundary places them or the host withdraws them" (spec.md:4559-4564) pd-doc. Nothing in the backend looks for this state today.

What breaks if not built

Now: after a run fails (for example a model API error or no credit left), a follow-up that the person queued stays in the queue strip. A program that waits on that submission through the SDK waits with no error and no time limit. With no person watching, the message never runs.

Later: any unattended agent that receives queued input, such as a proactive watcher sending follow-ups, stops responding after one failed run.

Files and sections
  • store.ts:885-887: inspect() already returns h.inspect(ctx): every live task with its state, and every queued or placed submission (spec.md:506-526).
  • New: Store.stuck(h) next to inspect(). C11 uses the same method.
  • routes.ts:94: next to /sessions/:s/inspect, a new GET /sessions/:s/stuck.
  • Existing action, unchanged: withdraw, routes.ts:151-152 → store.ts:845-847 (h.abortSubmission).
The change
// store.ts, next to inspect(). Reads only.
async stuck(h: Harness) {
  const { tasks, submissions } = await h.inspect(ctx);
  const busy = new Set(tasks.filter((t) => t.state.kind !== "blocked").map((t) => t.record.conversationId));
  return {
    blocked: tasks.filter((t) => t.state.kind === "blocked").map((t) => ({ taskId: t.record.id, reason: t.state.reason })),   // C11

A background job owned by the conversation counts as "busy" in this sketch. Whether queued follow-ups wait for such a job is not clear from the docs unverified, so C1's harness should add a case for it.

C6. Start even when the model catalog has gaps (G3-3)

What it is

Today the backend refuses to start if any of the 29 curated models is missing from pi-ai's OpenRouter catalog, or if the live model list does not load in 10 s. This change makes both cases a logged warning. The backend starts with the models that exist, and it fails only if none exist.

Why it is needed
  • store.ts:184-185: the constructor throws OpenRouter catalog missing <id> for the first missing model.
  • store.ts:282: getAvailable(..., { signal: AbortSignal.timeout(10000) }) throws on a timeout or an error. Store.open catches it, closes the store and throws again (store.ts:229-231), so main.ts:12 fails.
  • The service file has Restart=always and RestartSec=2 (apps/dpi-backend/deploy/dpi-backend.service:14-15). systemd starts the backend again every 2 s, and each attempt fails the same way. Whether systemd's default start limit stops the loop depends on how fast each attempt fails inferred.

C7. Detect a stale lock after a reboot (G3-4)

What it is

Each database has a lock file that holds the owner's process id (PID). After a crash, a new start removes the lock only if that PID is dead. This change also writes a boot identifier into the lock. A lock written during an earlier boot is always stale, even if its PID now belongs to another process.

Why it is needed

lockFile() writes String(process.pid) (store.ts:105). On EEXIST it sends signal 0 to that PID (lines 110-117). If any live process has that PID, startup fails with Database already owned by process N (line 118). After a reboot, PIDs are reused, so a lock left by a crash before the reboot can name a live, unrelated process.

pi-durable has no lock between processes (readme.md:547) pd-doc. This lock file is the only protection against two processes on one database, so the change must never make a live lock look stale.

What breaks if not built

Now: after a power loss or a crash followed by a reboot, the backend can refuse to start. All sessions stay paused until a person deletes the *.sqlite.lock file named in the error. The risk is higher with automatic restart (C10), because nobody is watching. Each start uses 3 kinds of lock: catalog.sqlite.lock, app-state.sqlite.lock, and one per session (lines 192, 214, 499).

Later: the same, with more sessions and more lock files.

Files and sections
  • store.ts:103-127: lockFile(). Three places change: take() (line 105), the stale check (lines 110-120), and the unlock closure (lines 122-126).
The change
  1. take() writes `${process.pid} ${bootId}`.
  2. Get bootId from a source that does not depend on the wall clock: on Linux and WSL2, the file /proc/sys/kernel/random/boot_id; on macOS, sysctl -n kern.boottime unverified as clock-independent. If neither works, write the PID only, as today.
  3. Stale check: if the file has a boot id and it is different from the current one, the lock is stale. Remove it and take it. Otherwise use today's PID check. A file with a PID only (the old format) uses today's PID check.
  4. unlock: compare the file with the exact string that take() wrote, not with String(process.pid). If this step is missed, a clean shutdown never deletes the lock, and every start after it depends on the stale check.

Do not compute the boot time as Date.now() - os.uptime() * 1000. A wall-clock change larger than the tolerance would make a live lock look stale, and two processes could then open one database.

Limit. A PID reused in the same boot (a crash, then an unrelated process gets that PID before the backend restarts) still blocks startup. Closing that case requires a check of the process command line (/proc/<pid>/cmdline on Linux, ps -o command= -p <pid> on macOS).

Group B: buildable in part (4)

C8. Make the Jev guard's gaps visible (G2-2)

What it is

One log line each time the Jev damage-control guard lets a bash command run without a verdict, plus a written rule for future hooks. This change does not make the guard stronger. It makes its gaps visible in backend.log.

Why it is needed

Three library behaviors limit any beforeTool guard pd-doc:

  • A hook runs outside the commit line and can run twice after a crash (spec.md:2545-2546). The Jev guard already handles this with a memo (addons.ts:122-125).
  • When a safe tool runs again after a crash, beforeTool is skipped. The rerun uses the conversation's current working directory, which can differ from the first attempt (spec.md:2917-2925, 4661-4663).
  • When Jev fails, the guard returns with no verdict and the command runs (addons.ts:126-128, "Fails open"). Nothing records that this happened.
What breaks if not built

Now: no data breaks. During a Jev outage (no key, a timeout, an error), every bash command runs unjudged and leaves no trace that the guard was skipped. The guard is off by default.

Later: a new hook that asks a person or an API and does not use a memo asks twice after a crash.

Files and sections
  • addons.ts:126-128: the catch branch of the Jev guard.
  • addons.ts:1-6: the file header, for the rule about hooks.
The change
  1. In the catch branch: console.error("[jev-damage-control] unjudged, ran anyway:", command, error message). backend.log receives standard error (dpi-backend.service:18-19).
  2. In the header: "A hook that asks a person or an outside API must store the answer with api.memo, as the Jev guard does."

Why not store the fail-open result in the memo. A memo disappears when the task ends (spec.md:1866-1869) pd-doc, so it is not a lasting record. Storing the fail-open result would also stop a second attempt to ask Jev if the hook runs again after a crash.

What stays open. The skipped beforeTool on a rerun and the current working directory on a rerun are library behavior. A check that must run on every execution must be inside the tool itself, and the built-in bash is a library tool. Whether the repo can replace it with its own bash wrapper is unverified.

C9. Backup of idle sessions to another disk (G2-6)

What it is

A route that copies a session's database to a backup folder while the session is idle. You point that folder to another disk or a synced folder. A scheduler you choose (cron in WSL2) calls the route.

Why it is needed

Each session is one agent.sqlite file on one disk. The code read for this plan has no copy, snapshot or replication step. archive() only renames the session folder into archive/ in the same data folder (store.ts:465-492).

What breaks if not built

Now: disk failure loses every session, all App State and the catalog. Also, an agent runs bash as the same user that owns ~/.dpi, so one wrong command from the agent can delete its own database inferred. The Jev guard is off by default and fails open.

Later: more sessions and longer histories at risk on one disk.

Files and sections
  • store.ts:464-492: archive(). The new backup() reuses its close sequence (lines 472-478) without the abort at lines 468-471.
  • store.ts:494-565: openAgent(), to reopen after the copy, then harness.resume().
  • routes.ts: a new POST /sessions/:s/backup, next to the other session routes (around lines 81-94).
  • Uses Store.stuck() / inspect() from C5 to check that the session is idle.
The change

Option A (inside the documented contract).

  1. Call h.inspect(ctx). If any task is live or any submission is queued, return "busy, try later".
  2. Close the harness and remove its lock, as archive() does. "Close writes no outcomes, so the work resumes on the next open" (spec.md:927-945) pd-doc.
  3. Copy agent.sqlite and any agent.sqlite-wal and agent.sqlite-shm files to <backup dir>/<session id>-<time>/.
  4. Call openAgent(row), then harness.resume().

A message that arrives during the copy waits until the reopen. The copy takes about as long as copying the file.

Option B (outside the documented contract). Open a second node:sqlite connection to the same file in the same process and use SQLite's online backup. The session does not close. readme.md:547 covers a second process, not a second connection in the same process. Whether this is safe is unverified.

What stays open. app-state.sqlite is one pi-durable harness shared by every session (apps/dpi-backend/src/shared-state.ts:36-37). Closing it for a copy stops every agent's update_state for that time. catalog.sqlite is a plain SQLite file that the repo owns (store.ts:193), so VACUUM INTO '<path>' on that connection copies it without a close. The off-disk destination and the schedule are your decision (open questions).

C10. Automatic restart on Windows through WSL2 (G2-7)

What it is

A way to restart the backend automatically on this Windows 11 machine, with the service file the repo already has. The backend runs as a systemd service inside WSL2. A Windows Task Scheduler entry starts WSL2 when you log on.

Why it is needed

The repo's restart layer is systemd (Restart=always, dpi-backend.service:14) or launchd (KeepAlive, dpi-backend.plist:21). There is no native Windows equivalent. The installer already supports a device of kind local with service: systemd: it fills deploy/dpi-backend.service and installs it with sudo -n systemctl enable and restart (drivers.ts:152-198, local path at line 156). WSL2 runs systemd when it is turned on in /etc/wsl.conf.

What breaks if not built

Now: on this machine, a crash or a reboot leaves every session paused until you run just backend run by hand. Nothing is lost. The proactive demo stops watching logs during that time.

Later: C6 and C7 matter less without automatic restart, because a person is present at each start. With C10, they matter more.

Files and sections
  • No code changes.
  • apps/dpi-backend/README.md:54: the service table. Add a Windows row.
  • Reused as they are: apps/dpi-backend/deploy/dpi-backend.service, drivers.ts:152-198.
The change
  1. In WSL2, add to /etc/wsl.conf: [boot] and systemd=true. Then run wsl --shutdown from Windows.
  2. In dpi-network.yaml, set the WSL2 device to kind local with service: systemd. Run just net up <id> from inside WSL2. This needs sudo -n (apps/dpi-backend/README.md:54).
  3. In Windows, create a Task Scheduler task that runs at log on and starts the WSL2 distribution, for example schtasks /Create /TN "dpi-backend WSL" /SC ONLOGON /TR "wsl.exe -d Ubuntu --exec /bin/true" unverified.
  4. Document steps 1–3 in the README row.

What stays open. Whether WSL2 keeps the VM running while only a systemd service runs, or shuts it down when idle, is unverified. A log-on trigger needs a log-on. A restart with nobody logged on needs a different trigger, also unverified. Test both after setup: reboot the machine, log on, and check systemctl status dpi-backend in WSL2.

C11. Report blocked tasks (G3-1)

What it is

The same Store.stuck() check as C5 also lists tasks that pi-durable cannot run because their definition is missing, too old, or failed to migrate. A person then puts the definition back, or ends the task with the existing abort route.

Why it is needed

A task whose definition is missing stays pending or waiting and is blocked with missing_task, task_too_old or migration_failed. It stays live and is never ended automatically (spec.md:611-623, 1997-2000) pd-doc. In this repo, job tasks are named demo.job.<id> with version: 1 (jobs.ts:719-723), and approvals are demo.job-approval (jobs.ts:376-378). Renaming a job id in JOB_DEFS (jobs.ts:64), or changing version without migrate, while a run is live, blocks that run.

What breaks if not built

Now: nothing, unless you edit the job definitions. No code in apps/ calls waitForIdle, so the "wait until idle hangs" case from the docs does not occur in this repo today.

Later: you rename or re-version a job while a run waits for approval (release-check waits for a person with no time limit). The run blocks. If run_durable_job started it with wait: true, the tool call that owns it (extensions.ts:231) waits forever. The conversation's run then never ends, and follow-ups queue behind it inferred.

Files and sections
  • The blocked line of Store.stuck() in C5. There is no extra code.
  • Existing action, unchanged: POST /sessions/:s/tasks/:taskId/abort (routes.ts:91-92 → store.ts:879-883).
The change

Only the report. To fix a blocked task, use one of two actions:

  1. Put the definition back (or add migrate). The task unblocks by itself, because a blocked task "is reconsidered whenever the registry changes" (spec.md:2000).
  2. Abort it. A blocked task cannot run its abort handler, so it ends orphaned, not aborted. "External effects the task started may remain uncleaned" (spec.md:2004-2013) pd-doc.

What stays open. The library decides when a task is blocked. The repo can only report it and choose one of these two actions. The lasting rule: keep old task definitions until no live task uses them.
