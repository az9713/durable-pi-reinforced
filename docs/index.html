Durable Pi: what it does, why it is durable, how

This page explains the durable-pi-main codebase for a person who has not read it. It covers what the code does, what "durable" means, how durability is implemented, what Pi and Jev do, and the facts a new user would not know to ask about.

1. What this repo does

This repo runs Pi coding agents as long-lived services on machines you own, and lets any client connect to them over HTTP. The agent survives a crash, a restart, or a closed browser, and continues from its last saved step.

Think of a normal coding agent as a phone call: if the line drops, the conversation is gone, and you must call back and explain again. A durable agent is more like a shared document with an autosave on every keystroke. Close the window, and the document is still there, at the exact point where you stopped. This repo puts that document on a server, so many windows (a browser, a terminal, a curl script) can open it at the same time.

The repo has five apps (README.md:269-293):

The central sentence of the README: "The device owns the run. Clients only watch and steer." (README.md:59).

2. The four parts: Pi, pi-durable, this repo, Jev

Four separate things work together. People often mix them up. Keep them apart:

Pi (the agent toolkit)

A family of npm packages from Earendil (earendil-works/pi). pi-ai talks to 15+ model providers. The Pi coding agent is a terminal CLI. This repo uses pi-ai for model access only. It does not run the Pi CLI.

pi-durable (the durable harness)

A library in the same family: @earendil-works/pi-durable. It runs the agent loop (model call, tool calls, model call…) and saves every step to storage before it shows the step. All durability lives here.

This repo (durable-pi)

An application on top of pi-durable, written by IndyDevDan (disler/durable-pi). It adds a device server, an HTTP API, a hub, a web UI, a TUI, deploy scripts, extra tools, "durable jobs", and the proactive demo.

Jev (the classifier)

A separate paid API from TypeSafe (typesafe.ai). It answers small, bounded questions about a JSON object ("is this log row normal, suspicious, or an incident?") in a few hundred milliseconds for about $0.00003 a call (README.md:80). It is not part of Pi.

clients (browser via hub · dpi-tui · curl) │ HTTP + SSE, bearer token ▼ dpi-backend ──────────────── this repo: routes, tools, jobs, App State, extensions │ Harness.open / conversation.submit / watchEvents ▼ pi-durable 1.0.3 ─────────── durability: tasks, checkpoints, replay, SQLite commits │ model requests ▼ pi-ai 1.0.3 → OpenRouter → Claude Sonnet 5.5, GPT, Gemini … Jev (TypeSafe API) ←── called by: proactive demo watcher (every log row) and the jev-damage-control hook (every bash command, opt-in)

4. Why is it "durable"?

"Durable" means: everything the agent does is written to disk before anyone sees it, so a restart can continue at the exact step where the work stopped.

Why /resume is not enough

The normal Pi CLI already saves a session as a JSONL file and has --resume (ai_docs/pi/sessions.md:13-34). The README explains what resume does not know (README.md:52):

Question after a crashPlain Pi /resumepi-durable
What did the conversation say?Yes: the transcript is saved.Yes: entries are committed.
Which tool call was running when the process died?No.Yes: each tool call is a task with a checkpoint.
Did that tool call already change something?No.Partly: the task knows it reached "execute". It cannot know whether the outside effect happened, so it tells the agent "interrupted".
What input was queued behind it?No. In plain Pi, "Abort returns queued messages to the editor" (ai_docs/pi/how-pi-works.md:17), so queued input lives in the client.Yes: queued input is the pi.inbox document.
What did the application believe was true?No. Pi docs say to keep data outside a session in external storage (ai_docs/pi/extensions.md:235).Yes: documents (App State, incidents, job runs) are committed in the same transaction as the entries.
A half-streamed model reply?Lost.Partial output is committed every 100 ms (partialIntervalMs). A crash loses at most that window pd-doc.

What durability gives you

Once a run survives the death of its own process, it no longer needs the window that started it. That single property produces every feature the video lists (README.md:249-255):

FeatureWhy durability is the cause
Long-running agentsClose the laptop, kill the process or restart the machine; the run resumes from its last checkpoint.
Multi-client agentsThe run lives on the device, so a browser, a TUI and curl are all just viewers of the same committed state.
Multiplayer agentsSeveral people can watch and steer one agent, because every viewer reads the same committed state.
Human near the loopAn approval is a durable task. It can wait hours, survive a restart, and still not run twice.
Proactive agentsCode can start an agent from an event with no person present, because no client window is needed.
Durable does not mean exactly-once. pi-durable guarantees exactly-once admission of a submission with a requestId. It does not guarantee that an outside effect (a payment, a page, a deploy) happens once. If the process dies after the effect but before the result is saved, a "safe" tool runs again and an "unsafe" tool reports "interrupted". Your effect needs its own idempotency key (README.md:332; ai_docs/durable_pi/announcement.md:153-155).

5. How pi-durable implements durability

The summary below covers the whole system. Sections 5.1–5.12 describe the library only, from its docs in ai_docs/durable_pi/ (mainly readme.md and the 4,696-line spec.md). The library source is not in this checkout, so treat every statement here as pd-doc. The spec uses the development name "Pico5" (ai_docs/durable_pi/sources.md:8). Size: about 15,000 lines of TypeScript without tests (announcement.md:66-69).

Executive summary: how "durable" works here

The short version. One library, pi-durable, does the durable work. It writes every step of an agent (each model call, each tool call, each piece of queued input, each document change) to a SQLite file in one atomic transaction before any client can see that step. When the process starts again, it reads the file and continues each unfinished step from its last saved checkpoint. A tool that was cut off runs again only if it is marked replay-safe; otherwise the agent gets an "interrupted" result and decides what to do. Everything else in the repo either keeps the process alive, prevents duplicates at the edges, or only watches.

Three rules carry all of it: (1) save, then show; (2) every step is a task with a checkpoint; (3) after a crash, rerun only what is safe to rerun, and report the rest as interrupted.

5.1 One commit line, and nothing is shown before it is stored

The core rule (spec.md:45-48): "A Session atomically commits immutable entries, full task records, and Chord-tracked documents. Only committed state is observable."

  • One line. Every change to a session goes through one serial queue (the "Session line"). There is no second writer, so there are no write conflicts inside a session (spec.md:1551-1561).
  • Atomic. One commit writes entries, task state and documents together, or writes nothing (spec.md:67-82).
  • Commit, then publish. A watcher sees a change only after the storage commit succeeds. "All visible progress is durable. There is no volatile publication path."
  • No outside effects inside a commit. Code must never wait for a model, the network or a person inside commit(), because that blocks the whole line (spec.md:4605-4607).
  • A doubtful storage failure is fatal. If the library cannot tell whether a commit was written, it "poisons" the session. You must reopen it (spec.md:4676-4677).

5.2 Tasks and checkpoints

A task is "a durable state machine that saves a checkpoint at every step" (readme.md:89). Each step (a "phase") returns a new checkpoint, and pi-durable commits it. On restart, the task continues from the last committed checkpoint.

ItemValuesRef
Built-in taskspi.generation (model call), pi.tool (tool call), pi.compactionspec.md:3261-3267

Define a custom taskdefineTask({name, version, initial, phases, abort, migrate?, hooks?})spec.md:1712-1725

One answered prompt produces this sequence of entries and tasks (readme.md:98-103):

pi.user (your input) └─ pi.generation task ── pi.system (only if the prompt or tools changed) └ pi.assistant (with tool calls) └─ pi.tool task × n ── pi.tool-result × n └─ pi.generation task ── pi.assistant (the answer)

The "effect sandwich" (spec.md:1853-1864) is the pattern every phase with an outside effect follows:

  1. Commit an intent checkpoint ("I am about to do X").
  2. Do the outside effect.
  3. Commit the outcome checkpoint.

If the process dies between step 1 and step 3, reopening finds the task in its intent phase. "Reopening in an intent phase means the effect may have happened." That is the exact uncertainty that the replay policy in 5.3 resolves.

A phase must make progress. If a phase handler returns the same checkpoint it received, the task ends faulted, "because no durable progress was made" (spec.md:1825-1826). A handler that throws also ends faulted.

5.3 Replay policy: safe, unsafe, interrupted

A tool task has two checkpoints: {phase:"call"} and {phase:"execute", arguments, replay} (spec.md:3572-3574).

  1. call: find the tool, validate arguments, run beforeTool hooks, validate again, then commit the intent: the final arguments, the replay policy, and slot status running. Then, in the same handler, execute the tool, run afterTool hooks, and commit the result (spec.md:3581-3590).
  2. execute: this phase "is reached only by recovery". It means the process died while the tool ran.

In the execute phase, pi-durable decides (spec.md:3591-3595, 3062-3067):

Stored policy (at call time)Current policy (after restart)Result
safesafeRun the tool again with the stored arguments.
safeunsafe or tool missingDo not run. Return an interrupted error result.
unsafeanythingDo not run. Return interrupted. A later safe never upgrades an earlier unsafe.

The interrupted result contains the partial output that was committed before the crash. The model reads it and decides what to do next. The README example: a bash call cut off by a restart comes back as interrupted, "so the agent decides what happens next instead of silently repeating a side effect" (README.md:58).

Other tool error codes: tool_unavailable, invalid_arguments, blocked, interrupted, aborted, tool_error (spec.md:3070-3074).

Three facts about a rerun. (1) A rerun does not run beforeTool hooks again; it uses the stored arguments. A safety hook therefore does not re-check a replayed call. (2) The rerun builds its environment with the conversation's current working directory, which can differ from the first attempt (spec.md:2917-2925, 4661-4663). (3) "Safe" means at-least-once. A safe tool that charges a card must pass its own idempotency key, for example `payment-${task.id}` (announcement.md:459-464).

5.4 Memos: remember a decision across a crash

A hook runs outside the commit line, so "a crash before the consuming commit may rerun" it (spec.md:2545-2546). If a hook asks a person or an API for a decision, a rerun would ask again. The fix is a memo:

  • api.memo(name) reads; api.memo(name, candidate) writes. The first writer wins. Write and read-back are one commit (spec.md:1866-1869).
  • A memo lives in the task's checkpoint envelope and is deleted when the task ends.
  • Hooks share the task's memo namespace, so prefix the name (this repo uses "jev-damage-control").

This repo's Jev guard stores its verdict in a memo, so a restart in the middle of a bash call does not ask Jev twice (apps/dpi-backend/src/addons.ts:94, 122-126).

5.5 Recovery when a session reopens

Harness.open does this (spec.md:611-623, 1834-1840):

  1. Every task that was running becomes pending. It keeps its checkpoint and any abort mark.
  2. Every task that was waiting stays waiting.
  3. Tasks in completing or waiting are checked again for finalization.
  4. A task whose definition is missing, too old or fails migration stays blocked with reason missing_task, task_too_old or migration_failed. Open never ends it. Install the extension and it unblocks.
  5. No handler runs during open. Work starts only after resume(), or after a call that asks for progress: submit, compact, abort, Submission.wait, waitForTask, waitForIdle (spec.md:633-642).

A model call that was streaming when the process died is handled like this (spec.md:3488-3497): the committed partial text becomes an aborted pi.assistant entry, then the same committed messages are sent again with the pinned model and settings. Aborted, errored and deferred assistant messages are excluded from later requests (spec.md:261-287).

Close (spec.md:927-945) stops new input, signals every running invocation, and waits for it to stop. It writes no outcomes, so the work resumes on the next open.

5.7 Queues and admission

  • submit({type:"input", content, requestId, whenBusy}). whenBusy is "followUp" (default), "steer" or "reject". "reject" throws ConversationBusy and writes nothing (readme.md:309-326).
  • type:"write" appends a passive entry and never starts generation.
  • Queued input is stored in the pi.inbox document. Steers are placed after the current tool round (postTools); follow-ups at the end of the run (final) (spec.md:2223-2226).
  • "requestId deduplicates within one conversation before any write" (spec.md:2203-2204). A retry returns the existing submission. harness.submission(id) finds a submission again after a restart.
  • Do not use the model provider's tool-call id as a requestId; it is not unique across a session. Derive ids from api.taskId (spec.md:2963-2964).

5.8 Documents

  • defineDoc({kind, version, scope, history, fork, initial, migrate?, checkpointWhen?}). scope is session, conversation or task. history is latest or rewindable. fork is asOf, current or initial (spec.md:949-1107).
  • Changes happen only inside commit((tx) => …) via tx.doc(token, id). Values must be strict JSON and are copied on assignment.
  • Storage holds a base value plus deltas (Chord Ops). checkpointWhen decides when a new base is written.
  • Built-in documents per conversation: pi.agent (model, tools, settings), pi.provider (a session UUID for the model provider), pi.live (the running state), pi.inbox (queued input), pi.usage (spend) (spec.md:655-670).
  • Inside the library there is no conflict detection, because the single commit line serializes writes. The 409 conflict you see in the web UI comes from this repo's App State code (6.6).

5.9 Compaction

Library defaults: {enabled:true, reserveTokens:16384, keepRecentTokens:20000, backgroundTokens:32768} (spec.md:384-394).

  • Background above contextWindow − reserveTokens − backgroundTokens: a separate task writes a summary while the agent keeps working.
  • Blocking above contextWindow − reserveTokens: the next model call waits for a summary.
  • Overflow: if the provider reports a context overflow, compact and retry once. A second overflow fails as model_error (spec.md:3515-3524).
  • The summary is a pi.compaction entry with a head marker. The old entries remain in storage, and this repo's search_history tool can still find them.
  • Each compaction costs one summarization model call, even when a newer summary replaces it and it ends stale (spec.md:4565-4567).

This repo changes the thresholds; see 6.7.

5.10 Forks, subagents, workflows, waiting

  • Fork: the new conversation sees the parent's entries up to entry E without copying them. It gets a fresh provider session id and an empty inbox. Each document follows its fork policy (spec.md:1499-1547).
  • Foreground subagent: a tool creates a conversation owned by its own task id. On a replay-safe rerun, the tool first looks for its existing child with tx.scanConversations({ownerTaskId}), so it does not create a second child (spec.md:2958-2997).
  • Workflows: a custom task can create child tasks and commit {status:"waiting", on:[ids], policy:"failFast"|"allSettled"}. While waiting, it runs no code. runtime.sleep(until) is a timer that survives restarts (readme.md:466-487).
  • Waiting for a person: pi-durable has no built-in approval primitive. A task can wait only on other tasks, not on a document or an outside signal. The documented pattern is a beforeTool hook that asks a person and stores the answer in a memo (announcement.md:406-428). This repo builds approvals differently, with a child task that polls a document (6.5, 9).

5.11 Extensions and hooks

  • defineExtension({name, tools, sections, hooks, wraps, tasks}), installed with registry.install(). Reinstalling the same name replaces it in place. The registry lives in process memory; a conversation stores only extension names (spec.md:2279-2461). An extension must therefore be installed on every start, before open.
  • defineTool({name, description, parameters, replay, execute, …}). Default output limit: 50 KiB or 2,000 lines.
  • Hooks: beforeRequest, afterResponse, onYield, afterTools on the generation task; beforeTool (rewrite args or {block}; a throw also blocks) and afterTool on the tool task; beforeCompact on the compaction task (spec.md:2548-2620).
  • Prompt sections render on every request. A change is stored as a pi.system entry with only the difference, which keeps the provider's prompt cache valid. Text that changes on every render (a timestamp, for example) adds an entry every time and breaks caching (spec.md:4664-4669).
  • Because tools and settings are read on every request, the tool set, model and thinking level can change mid-run. The next request uses the new values. This is the mechanism behind the "Read only" switch in the video.

5.12 Streams to clients

  • watchEvents() emits one batch of events per commit: snapshot, message_update, tool_execution_*, compaction_start/end and more. It is marked experimental (spec.md:4050-4193).
  • A slow watcher keeps at most 100 pending frames or batches. After that it gets one fresh full snapshot. "Nothing is replayed" on reconnect (readme.md:294-305).
  • Streams drop intermediate states by design. They are not an audit log (spec.md:4630-4634).

6.2 Startup sequence and locks

  1. Load config: flags, then env file (--env-file, DPI_ENV_FILE, or $DPI_HOME/backend.env). Startup fails if DPI_TOKEN is shorter than 32 characters (src/config.ts:30-52).
  2. Lock and open catalog.sqlite, then lock and open App State.
  3. For every catalog row, lock and Harness.open its agent.sqlite, with a registry that installs CodingTools, the playground extension and the two add-ons. A session that fails to open is reported as 503 unavailable; the others continue (store.ts:217-223, 494-565).
  4. Load the model list with models.getAvailable("openrouter") (10 s timeout; whether this is a network call is unverified). If that fails, startup fails (store.ts:229-231, 282).
  5. Only then call harness.resume() on every session. Interrupted work restarts at this point (store.ts:227).
  6. Listen on DPI_HOST:DPI_PORT (default 127.0.0.1:4780).

Locks (store.ts:103-127): a lock is a file holding the owner's PID, created with exclusive mode. If the file exists, the code checks whether that PID is alive (process.kill(pid, 0)). A dead PID means the lock is stale and is taken over. The recovery test kills the server with SIGKILL and restarts it; this path takes over the stale locks (tests/recovery.test.ts:8-31).

The agent's shell environment is a whitelist: PATH, HOME, USER, SHELL, TMPDIR, LANG, TERM (store.ts:501-505). DPI_TOKEN and OPENROUTER_API_KEY are not passed to bash. (See 12 for why this does not fully protect them.)

6.3 Sending work

POST /v1/sessions/:s/agents/:a/messages with {content, requestId, whenBusy?, waitMs?} (store.ts:808-816, routes.ts:137-149):

  • content: 1–100,000 characters. requestId: required, ≤ 128 characters.
  • The backend calls conversation.submit({type:"input", content, requestId, whenBusy}). The same requestId returns the same submission id (tests/api.test.ts:55-56).
  • whenBusy:"reject" on a busy agent returns 409 busy.
  • waitMs (max 300,000) turns the call into a one-shot request: the server waits for the answer and returns 200 {status:"done", answer:{entryId, text}}, or 202 if time runs out. Without waitMs the response is 202 {status:"queued"}.

6.5 Durable jobs

Jobs are the repo's example of a multi-step workflow that survives restarts (src/jobs.ts:64-120). Each saves its result to App State under /jobs/<id>.

JobPhasesInputs
workspace-snapshotscan → measure → save → verifypath (default .)
release-checkplan → gather (a subagent) → approve (waits for a person) → publish → verifycommits 1–20 (default 5)
change-watchbaseline → watch (repeats) → reportpath; checks 2–20 (default 5); interval_seconds 2–60 (default 4)

How a job runs (jobs.ts:667-737): each job is one pi-durable task demo.job.<id>, with checkpoint {phase, iteration, data, approvalTask?}.

  1. Before each phase except the first, a durable runtime.sleep of 900 ms.
  2. An entry commit marks the phase as started. If it finds steps from the same iteration, a crash interrupted it: those steps are discarded, resumed is incremented, and the note "Resumed from the last checkpoint after a restart" is added.
  3. The handler runs. It returns {done} (commit the next phase) or {again} (commit the same phase with iteration + 1; change-watch uses this for one checkpoint per check).

Granularity. Resumption is per phase and iteration. A resumed phase runs its handler from the start, so its shell commands run again. Writes stay single because each App State write uses a receipt key job:<session>:<task>:<phase>:<iteration>:<path> (jobs.ts:439, 456-470).

How approval waits (jobs.ts:376-400, 622-665):

  1. One commit sets run.approval = "pending", creates a child task demo.job-approval, and moves the job to {status:"waiting", on:[approvalTask], policy:"allSettled"}.
  2. The child task reads the run record every 500 ms with a durable sleep. It writes nothing until the value changes.
  3. A person clicks Approve or Decline: POST …/demo/jobs/:taskId/approval flips the value in one commit. A second click returns 409 conflict.
  4. The child completes; the job wakes, reads the outcome, and continues or fails ("declined").

The pending approval survives a restart (tests/store.test.ts:86-92).

6.6 App State (shared state)

  • One JSON document per device, stored in its own harness (app-state.sqlite), so every session on the device sees the same value, and a fork always sees the current value.
  • Each change is one path operation: create (fails if the key exists), update, delete, increment (numbers only). Paths are JSON Pointers. __proto__, constructor and prototype are rejected. Limits: depth 24, 100,000 characters total (apps/dpi-sdk/src/app-state.ts).
  • Each successful change increments a revision. A full-document save sends expectedRevision; a stale value returns 409 conflict.
  • A change with a receipt key is checked against the receipt before the revision, so a replayed tool call succeeds even if the revision moved (shared-state.ts:62-81).

6.8 API, streams and auth

  • Auth: Authorization: Bearer <token> or X-DPI-Token. Both sides are SHA-256 hashed and compared with timingSafeEqual (src/auth.ts). GET /healthz needs no token; everything under /v1 does. No rate limiting.
  • Routes: the full list is in apps/dpi-backend/API.md. Sessions and agents are addressed by id or by unique case-insensitive name: /v1/sessions/release-notes/agents/main.
  • Streams (SSE): device (/v1/events), session, and agent. Every stream sends hello, then a snapshot, then deltas. A : ping comment every 15 s. A viewer more than 2,000,000 bytes behind is disconnected (src/streams.ts:20-74).
  • No replay: Last-Event-ID is ignored. A reconnect gets a fresh snapshot. Closing a stream never stops work (streams.test.ts:92-94).
  • Two dedupe mechanisms: requestId for messages; an Idempotency-Key header for three create routes only (POST /sessions, POST …/agents, POST …/fork).

6.9 Walkthrough: kill the device in the middle of a tool call

This is the scenario just test e2e runs on a real device (README.md:319). Read it as one end-to-end story of the parts above.

  1. You type "run the test suite and fix failures" in dpi-tui. The TUI sends it with a fresh requestId. The backend calls submit; pi-durable commits a pi.user entry and a pi.generation task in one transaction.
  2. The web client, open on the same agent, receives the commit through its SSE stream and shows the message. It never talked to the TUI.
  3. The model streams a reply. Every 100 ms the partial text is committed to pi.live. The model asks for bash npm test. A pi.tool task commits its intent (execute phase, arguments, replay policy) and starts the process.
  4. You close both clients. Nothing changes on the device: clients only watch.
  5. The device restarts (power cycle, just net restart, crash). The bash process dies with it.
  6. systemd or launchd starts dpi-backend again. It finds the old lock files, sees the PIDs are dead, takes the locks, opens each session, and calls resume().
  7. pi-durable finds the tool task in its execute phase. bash is not replay-safe, so it does not run npm test again. It commits an interrupted result with the partial output that was saved.
  8. The generation task continues. The model reads "interrupted", decides to run the tests again, and continues normally.
  9. You run just tui attach mac-mini:api-refactor:main. The TUI gets a fresh snapshot and shows the whole run, including the interrupted call. The e2e result: "9 tool results, 1 interrupted by the restart, each prompt admitted once" (README.md:319).

  • Memoized with api.memo("jev-damage-control"), so a restart does not ask again. Memos live in the task's checkpoint envelope, so the scope is one tool call pd-doc.
  • Fails open: no key, a timeout, or an error means the command runs. Worst case before it runs: 3 × 15 s + 2.4 s backoff ≈ 47 s inferred.
  • With the faux provider it uses an offline regex instead of the API.
  • It covers bash tool calls only. Not write or edit, not job shell commands, not the release-check subagent's bash inferred.

How the incident agent starts with no person

  1. The watcher's threshold is met. Code (not the agent) opens the incident in one harness.commit: increment seq, create the conversation, configure it, write the incident document (ops.ts:125-180).
  2. Code submits the brief with requestId: "incident:<id>:brief". If the backend restarts, recover() submits the same brief again; the requestId makes the second submit a no-op (ops.ts:117-123, 189-196).
  3. The agent follows the incident_playbook prompt section: investigate → root cause → fix + regression test → submit_fix → short review note → deploy (extensions.ts:466-486).

Why the deploy cannot run twice

The deploy tool creates a durable task ops.deploy owned by the tool call, with phases approval → rollout → verify. The approval phase reads the ops.deploys document every 400 ms through a durable sleep. The code comment states the reason: "Durable Pi has no built-in signal" (extensions.ts:243). Five independent mechanisms keep the deploy single:

  1. A replay of the same tool call finds the existing deploy by toolTaskId === api.taskId and returns it (extensions.ts:369-372).
  2. The deploy task's phases are checkpoints. A restart resumes the current phase; it does not start over.
  3. POST /api/deploys/:id/decide changes the status only if it is still awaiting_approval (ops.ts:306-316).
  4. The log stream ignores a deploy request whose id equals the last deployed.id (apps/proactive-dpi-logs/src/main.ts:96).
  5. The "ready" voice flag is set in the same commit as the task, so the announcement does not repeat after a crash.

This is the repo's practical answer to "durable is not exactly-once": the effect (the rollout) carries its own idempotency key (the task id), checked by the receiver.

Guardrails on the incident agent

  • A beforeTool regex on bash blocks git push, merge, rebase, switch, worktree, reset --hard, branch delete/rename, and checkout of new branches or main/master. Message: "Blocked by the incident guard… A human reviews and merges." (extensions.ts:460-461, 488-500).
  • API keys are kept out of the agent's shell; test runs get only PATH and HOME (ops.ts:72-77, repo.ts:40).
  • Tool calls run one at a time (toolExecution: "sequential"), chosen for a readable timeline (ops.ts:86-87).

11. Run it (and the Windows facts)

Read before you run on Windows. The original repo targets macOS and Linux. No file in the original repo mentions Windows or WSL. Facts checked on one Windows 11 machine during the research (2026-10-12):
  • The justfile and every just/*/mod.just set shell := ["zsh", "-cu"] with no windows-shell. zsh is not installed here, so every just recipe fails natively.
  • Node here is v22.22.0. The README and /install require Node 24. The backend's engines field accepts ≥ 22.19. The proactive demo README requires 24.14+.
  • rsync and lsof are not installed. just/free-port.sh exits 0 silently when lsof is missing, so it does not free the port.
Likely failures found by reading the code unverified:
  • DPI_START_DIRS is split on : (apps/dpi-backend/src/config.ts:40-43), so a path like C:\work splits into C and \work.
  • apps/proactive-dpi-demo/scripts/demo.ts:37 spawns node_modules/.bin/tsx without a shell. On Windows the shim is tsx.cmd.
  • voice.ts:49 builds a URL with path.split("/"); Windows paths use \, so browser voice breaks.
  • just proactive stop uses pkill, open is macOS-only, afplay is macOS-only.
  • The registry's mode-600 permission is a POSIX permission; Windows does not enforce it the same way.
Recommendation inferred: run the repo inside WSL2 (Ubuntu) with Node 24, zsh and just installed there, and keep the clone on the Linux file system (~/), not under /mnt/c. node_modules is not portable between Windows and WSL because it holds platform binaries (esbuild, oxlint).

12. Unknown unknowns

These are facts a new user would not know to ask about. Each item gives the likely assumption, what the code does, and what to do.

Short file names in this section: store.ts, jobs.ts = apps/dpi-backend/src/; watcher.ts, watch-store.ts, ops.ts = apps/proactive-dpi-demo/apps/proactive-dpi-be/src/; deploys.ts = apps/proactive-dpi-demo/apps/proactive-dpi-logs/src/; guard.ts = apps/dpi-playground/apps/dpi-playground-hub/src/; registry.ts = apps/dpi-sdk/src/node/; spec.md, readme.md = ai_docs/durable_pi/.

Durability guarantees

"Durable" does not mean "every effect happens exactly once"

Assumption
After a crash, the system makes sure each action happened once.
Reality
Only admission of a submission with a requestId is exactly-once. A replay-safe tool reruns (at-least-once). An unsafe tool reports "interrupted" and the effect may or may not have happened (README.md:332).
Action
Give every outside effect its own idempotency key, as the demo deploy does with the task id (9).

A power cut can lose the newest commit

Assumption
Anything shown in the UI is on disk forever.
Reality
SQLite runs in WAL mode with synchronous = NORMAL: commits survive a process crash, "the newest may be lost on power or host failure" (ai_docs/durable_pi/readme.md:544) pd-doc.
Action
Treat the last second before a power loss as uncertain. For hard guarantees on a device, use a UPS or a VM host with durable disks.

A safety hook does not run again on a replayed tool call

Assumption
A beforeTool guard checks every execution.
Reality
On recovery, a replay-safe tool reruns with the stored arguments and beforeTool is skipped (spec.md:2917-2925) pd-doc. The guard decided once, at call time.
Action
Accept this for guards whose decision does not change. Put checks that must run on every execution inside the tool itself.

A hook can run twice; a phase that changes nothing is "faulted"

Assumption
Hooks and task phases run once.
Reality
Hooks run outside the commit line and can rerun after a crash. A phase that returns its input checkpoint unchanged ends faulted (spec.md:1825-1826, 2545-2546) pd-doc.
Action
Store hook decisions in a memo. Make every phase return a changed checkpoint.

Queued follow-ups can wait forever after a failed run

Assumption
A failed run processes the queue anyway.
Reality
After a failed run, queued follow-ups stay in pi.inbox, and their wait() does not settle until the next submission or a withdrawal (spec.md:4559-4564) pd-doc.
Action
After an error, send a new message or withdraw the queued item (the X on the queue strip).

Removing an extension can freeze tasks

Assumption
Old tasks from a deleted extension fail and disappear.
Reality
A task whose definition is missing at open stays blocked (missing_task) and still counts as live, so "wait until idle" can hang (spec.md:611-623) pd-doc.
Action
Keep task definitions (with migrate) until old sessions have no live tasks of that kind.

A resumed job phase repeats its shell commands

Assumption
Jobs resume at the exact step.
Reality
Resumption is per phase and iteration. The phase handler runs from the start again; only App State writes are deduplicated by receipt (jobs.ts:676-694).
Action
Keep each phase's shell work safe to repeat, as the three example jobs do.

Security

A device token is a shell on that device

Assumption
The token only lets you chat with an agent.
Reality
Anyone with the token can make an agent run bash as the device's user. start_dirs only set where sessions begin; any existing directory is accepted as a working directory (store.ts:398-406; README.md:333).
Action
Treat tokens like ssh private keys. Run devices as a dedicated low-privilege user, ideally on a machine reserved for agents, as the video does with its M6 Mac mini video.

The agent can read its own API keys from disk

Assumption
Keys are hidden because the agent's shell environment does not include them.
Reality
The shell env is a whitelist (store.ts:501-505), but ~/.dpi/backend.env holds DPI_TOKEN and OPENROUTER_API_KEY and runs as the same user. A read or cat of that file works inferred. A prompt injected through a log line or a web page could ask for it.
Action
Use a key with a spending limit. Do not give agents untrusted input on a device that holds valuable keys.

The hub has no login

Assumption
The Host/Origin guard protects the hub.
Reality
The guard blocks browsers on other sites. A request with no Origin header (curl, any local program) passes. The hub holds every token and proxies every route, including session deletion (guard.ts:15-25). Binding the hub to a non-loopback address exposes every device.
Action
Keep the hub on 127.0.0.1. Treat any local process as able to control your devices.

exe.dev devices are public on the internet; LAN devices send tokens in clear text

Assumption
A cloud sandbox is private.
Reality
just net up runs share set-public for exe-dev devices; the bearer token is the only gate. ssh devices on the LAN speak plain HTTP (README.md:334). ssh uses StrictHostKeyChecking=accept-new (trust on first use).
Action
Rotate tokens (just net rotate <id>) after any doubt. Use a VPN (for example Tailscale) for LAN devices.

Read-only mode only limits the model

Assumption
A read-only agent cannot change anything.
Reality
It removes 8 tools from the model's list. The REST routes /demo/jobs and /demo/state still run jobs (with shell commands) and change App State on that agent (store.ts:1098-1143).
Action
Use read-only as a safety switch for the model, not as an access control for clients.

The demo's git guard is a regex, and approving a deploy runs agent code

Assumption
The incident agent cannot touch main, and the approved code runs in a separate service.
Reality
Forms such as git -C … push, git -c x=y push and update-ref do not match the pattern, and write/edit are not checked inferred. The log stream import()s the approved commit into its own process (deploys.ts:31). The demo has no login and binds 127.0.0.1 by default.
Action
Keep the demo on loopback. Review the diff ("View diff") before you approve.

Jev

The damage-control guard fails open and has gaps

Assumption
With jev-damage-control on, destructive commands cannot run.
Reality
No key, an error or a timeout lets the command run. It checks bash tool calls only. It sends every command's text to a third-party API (README.md:337). It is off by default.
Action
Treat it as a seat belt, not a sandbox. Use OS-level isolation (a dedicated user, a VM) for real protection.

A Jev outage leaves rows unjudged for good

Assumption
When Jev recovers, the backlog is judged.
Reality
A row that fails is recorded as error and never re-judged. Only rows in flight at a backend restart are re-judged (watcher.ts:155-157). The demo still recovers because the bug keeps producing new failing rows inferred.
Action
In production, add a retry queue for error rows, or a cheap code pre-filter (the video suggests checking 4xx/5xx status first video).

The incident threshold counts low-confidence rows

Assumption
All 3 counted verdicts passed the 0.6 probability gate.
Reality
The 0.6 gate applies to the current row only. Earlier rows with the same fingerprint count at any probability. The window uses log timestamps, not judge time (watcher.ts:165 vs watch-store.ts:139-146).
Action
If false alarms matter, filter the count by probability too.

Proactive demo behavior

One fingerprint opens one incident, ever

Assumption
If the same error comes back next week, a new incident opens.
Reality
The open-fingerprint set is rebuilt from the incident document on restart, and blocks a repeat even after the incident is Deployed (ops.ts:126, 134).
Action
Run just proactive take (it resets) for a new take. In a real system, release the fingerprint when the incident closes.

Interrupting a deploy after rollout does not roll back

Assumption
Interrupt cancels the deploy.
Reality
cancelDeploy withdraws only a request the stream has not picked up. After pickup, the new revision stays live while the deploy shows cancelled (watch-store.ts:243-246) inferred.
Action
Decide at the approval step, not during rollout.

Operations

A stale lock with a reused PID blocks startup

Assumption
After a crash, the backend always restarts.
Reality
A lock is taken over only if its PID is dead. If a reboot gives that PID to another process, startup fails with "Database already owned by process N" (store.ts:110-119).
Action
Check that no dpi-backend runs, then delete the *.sqlite.lock file named in the error.

A pi-ai upgrade or an OpenRouter outage can stop the server from starting

Assumption
A missing model only disables that model.
Reality
Startup throws if any of the 29 curated models is missing from pi-ai's OpenRouter catalog, or if the model list cannot load in 10 s (store.ts:184-185, 282). Whether the list load needs the network is unverified. A stored model that is no longer curated is silently replaced by the default anthropic/claude-sonnet-5.5 (store.ts:302-312).
Action
Keep the pinned versions together. Check apps/dpi-backend/src/model-catalog.ts after any upgrade.

One registry for every checkout; it prunes tokens

Assumption
Two clones of the repo keep separate device lists.
Reality
All clones share ~/.dpi/network.sqlite. Every hub start, TUI start and just net command syncs the YAML and deletes config devices that are not in it, tokens included (registry.ts:202-205).
Action
Use one dpi-network.yaml, or set DPI_HOME per clone.

New YAML devices need a hub restart

Assumption
The hub sees a new device in the YAML automatically.
Reality
The hub seeds the registry once at boot, and only starts monitor loops at boot or on "Check now". The cookbook's "picks it up automatically" (cookbook/dpi-network.md:92) does not match the code (apps/dpi-playground/apps/dpi-playground-hub/src/main.ts:27-30).
Action
Restart just hub start after you add a device.

Compaction settings stick after you change models

Assumption
Thresholds follow the current model's window.
Reality
After any manual change, the full settings object is saved and no longer derived. A switch to a smaller model refits and saves; a switch back does not restore 200k/250k (store.ts:799-803, 1028-1031).
Action
Re-drag the context-bar markers after a model change.

Two clients, two Enter behaviors

Assumption
Enter does the same thing everywhere.
Reality
In the TUI, Enter on a busy agent steers (joins the current run). In the web composer the default is follow-up (waits for the run to end).
Action
Use Alt+Enter in the TUI to queue.

Two processes must never open one session database

Assumption
You can open agent.sqlite with a second tool while the backend runs.
Reality
pi-durable has no cross-process lock; the repo's PID lock is the only protection. A second writer is unsupported (readme.md:547). Read-only inspection with sqlite3 is outside the documented contract unverified.
Action
Use the API (/inspect, /entries, /transcript) to read state.

Storage grows without a cleanup job

Assumption
Old data is removed.
Reality
Entries are never deleted (that is how search_history works). App State receipts are never pruned. Archiving a session leaves its compaction and spawn rows in the catalog (store.ts:487-488) inferred.
Action
Archive old sessions and delete backend/archive/ by hand when needed.

pi-durable is experimental

Assumption
This is ready for production.
Reality
"The API changes without notice between releases" (ai_docs/durable_pi/readme.md:7). Version 1.0.3 (2026-10-05) already had breaking environment API changes (changelog.md:9-37). The video author says he will not deploy it to production until a stable V1 video.
Action
Pin exact versions (the repo does). Read the changelog before each upgrade.
